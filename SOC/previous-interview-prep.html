Gold Standard Incident Process

NIST-style CSIRT/SOC workflow
1. Preparation

Goal: be ready before the incident happens.

  • Define severity levels, escalation paths, communication rules, and response playbooks.
  • Confirm logging is enabled for identity, endpoint, firewall, DNS, proxy, email, VPN, cloud, and critical applications.
  • Know who owns containment actions: endpoint isolation, account disablement, firewall blocks, email purge, server shutdown, or legal/compliance notification.
  • Applications: ServiceNow, Splunk, Microsoft Sentinel, Defender, CrowdStrike, Tenable/Nessus, asset inventory, CMDB, email-security tools, firewall consoles.
2. Detection And Initial Analysis

Goal: decide whether the alert is real and what it means.

  • Start at the source of the alert: Splunk/Sentinel for SIEM alerts, EDR for endpoint alerts, email console for phishing reports, firewall/proxy for network alerts.
  • Record the alert source, time, user, host, IPs, process, domain, file hash, severity, and detection rule.
  • Determine whether activity was attempted or successful, allowed or blocked, expected admin work or suspicious behavior.
  • Applications: Splunk, Sentinel, Elastic/Kibana, CrowdStrike, Defender, Windows Event Viewer, PowerShell logs, DNS/proxy/firewall logs.
3. Triage And Prioritization

Goal: decide how serious it is and how fast to act.

  • Ask: is the asset critical, internet-facing, privileged, regulated, or tied to sensitive data?
  • Look for high-risk signs: malware execution, credential theft, ransomware behavior, lateral movement, exfiltration, persistence, or privileged-account abuse.
  • Set severity based on impact, confidence, scope, and active risk.
  • Applications: ServiceNow severity fields, CMDB/asset inventory, EDR severity, SIEM notable events, vulnerability scanner context, threat intel platforms.
4. Scoping

Goal: determine blast radius before overreacting or underreacting.

  • Pivot by host, user, source IP, destination IP, domain, file hash, process name, parent process, command line, mailbox, and time window.
  • Search for the same IOC or behavior across the environment.
  • Separate one affected system from a campaign affecting many users or hosts.
  • Applications: Splunk/Sentinel/Elastic for broad search, EDR for host spread, email-security console for recipient scope, firewall/proxy/DNS for network scope.
5. Containment

Goal: stop damage or spread while preserving enough evidence to understand what happened.

  • Short-term containment: isolate host, disable account, revoke sessions, block IP/domain/hash, quarantine email, stop malicious process, restrict network segment.
  • Long-term containment: temporary firewall rules, password resets, conditional access changes, patch or config change, remove exposed service.
  • Contain immediately for ransomware, active malware, lateral movement, privileged compromise, data exfiltration, or business-critical risk.
  • Applications: CrowdStrike/Defender host isolation, Active Directory/Entra ID, firewall/proxy consoles, email-security tools, ServiceNow change/incident records.
6. Eradication / Remediation

Goal: remove attacker access and fix the weakness that allowed it.

  • Remove malware, persistence, suspicious scheduled tasks, rogue services, malicious mailbox rules, bad OAuth grants, exposed credentials, or unauthorized accounts.
  • Patch vulnerable systems, fix misconfigurations, rotate secrets, harden access, and close abused ports or services.
  • Verify that the original access path is closed, not just the visible symptom.
  • Applications: EDR cleanup actions, patch management, Tenable/Nessus validation, AD/Entra ID, ServiceNow remediation tasks, vulnerability management tooling.
7. Recovery

Goal: restore normal operations safely.

  • Restore from clean backups if needed, re-enable accounts only after reset/session revocation, reconnect hosts only after validation.
  • Monitor closely for repeat indicators, callbacks, suspicious logons, or re-created persistence.
  • Confirm business owner acceptance before declaring recovery complete.
  • Applications: backup platforms, EDR monitoring, SIEM dashboards, ServiceNow task closure, vulnerability rescans, asset owner sign-off.
8. Reporting And Lessons Learned

Goal: make the organization better after the incident.

  • Write timeline, root cause, impact, affected assets, containment actions, remediation, evidence, communications, and open follow-up items.
  • Identify control gaps: missing logs, weak detection, poor MFA, exposed service, patch delay, unclear escalation path, or user-training gap.
  • Create follow-up tickets for detection tuning, playbook updates, patching, hardening, training, or architecture changes.
  • Applications: ServiceNow incident report, Confluence/SharePoint knowledge base, SIEM detection backlog, Jira/Azure DevOps tasks, executive summary documents.

Keywords And Lingo
Incident Terms
  • Event: any observable activity in a system or network.
  • Alert: a tool-generated signal that something may need review.
  • Incident: confirmed or suspected activity with negative security impact.
  • Case / Ticket: the tracked record of investigation, evidence, actions, and ownership.
  • Severity: priority based on impact, scope, asset criticality, and confidence.
Triage Language
  • Validate: prove whether the alert is real or noise.
  • Scope: determine how many users, hosts, systems, or accounts are affected.
  • Pivot: use one artifact to search for related evidence.
  • Enrich: add context like asset value, user role, IP reputation, geolocation, or vulnerability status.
  • Correlate: connect evidence from multiple tools into one story.
Evidence Terms
  • IOC: indicator of compromise, such as IP, domain, hash, URL, file path, registry key.
  • TTP: tactic, technique, and procedure; how the attacker behaves.
  • Process tree: parent-child execution chain on an endpoint.
  • Hash: file fingerprint used for reputation and matching.
  • Telemetry: data produced by systems, tools, logs, agents, and sensors.
Containment Terms
  • Isolate host: cut endpoint network access while keeping EDR control.
  • Disable account: stop identity-based access during suspected compromise.
  • Revoke sessions: invalidate active tokens/logins after credential risk.
  • Block IOC: prevent known bad IP/domain/hash/URL from communicating or executing.
  • Quarantine: remove or restrict malicious email/file from user access.
Tool Names
  • SIEM: Splunk, Microsoft Sentinel, Elastic/Kibana; broad log search and correlation.
  • EDR/XDR: Defender, CrowdStrike; endpoint process, file, and isolation evidence.
  • ITSM: ServiceNow; incident tickets, ownership, approvals, status, reporting.
  • Vulnerability scanner: Tenable/Nessus; exposed weakness and remediation validation.
  • Threat intel: VirusTotal, MISP, vendor intel, ISAC feeds; reputation and context.
Outcome Terms
  • False positive: alert fired on benign activity.
  • True positive: alert correctly identified malicious or policy-relevant activity.
  • False negative: malicious activity occurred but no alert fired.
  • Root cause: original weakness or access path that enabled the incident.
  • Lessons learned: post-incident improvements to tools, process, people, and controls.

Hashing, Algorithms, And Syntax

File reputation and evidence checks
PowerShell: check a file hash

Use Get-FileHash to fingerprint a suspicious file before searching EDR, SIEM, VirusTotal, tria.ge, or internal threat intel.

Get-FileHash -Path "C:\Users\Ames\Downloads\suspicious.exe" -Algorithm SHA256
Get-FileHash -Path "C:\Users\Ames\Downloads\suspicious.exe" -Algorithm MD5
Get-FileHash -Path "C:\Users\Ames\Downloads\suspicious.exe" -Algorithm SHA1

# Hash every executable in a folder
Get-ChildItem "C:\Temp" -File -Recurse |
  Where-Object { $_.Extension -in ".exe",".dll",".ps1",".js",".vbs",".bat" } |
  Get-FileHash -Algorithm SHA256
Common hash algorithms
  • MD5: old 128-bit hash. Fast and common in older tools, but collision-broken. Use for legacy lookup only, not trust decisions.
  • SHA1: old 160-bit hash. Also collision-weakened. Still seen in logs and older reputation sources.
  • SHA256: modern standard for file reputation, malware matching, and evidence notes. Use this by default in SOC work.
  • SHA512: stronger/larger SHA-2 hash. Less common in day-to-day SOC triage than SHA256.
  • Imphash: import hash for Windows PE files. Useful for clustering malware families with similar imported functions.
  • SSDeep / fuzzy hash: similarity hash. Useful when files are not identical but are related variants.
PowerShell: quick process, network, and event checks 
# Running processes with path and command line
Get-CimInstance Win32_Process |
  Select-Object ProcessId,ParentProcessId,Name,ExecutablePath,CommandLine

# Network connections with owning process ID
Get-NetTCPConnection |
  Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess

# Recent failed logons
Get-WinEvent -FilterHashtable @{LogName="Security"; Id=4625; StartTime=(Get-Date).AddHours(-24)}

# Recent successful logons
Get-WinEvent -FilterHashtable @{LogName="Security"; Id=4624; StartTime=(Get-Date).AddHours(-24)}

# PowerShell script block logs
Get-WinEvent -FilterHashtable @{LogName="Microsoft-Windows-PowerShell/Operational"; Id=4104}
Windows persistence checks 
# Scheduled tasks
Get-ScheduledTask | Where-Object State -ne "Disabled"

# Services
Get-CimInstance Win32_Service |
  Select-Object Name,State,StartMode,PathName

# Common run keys
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run"

# Startup folders
Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"
Get-ChildItem "C:\ProgramData\Microsoft\Windows\Start Menu\Programs\StartUp"

Email Phishing Scenarios

Step-by-step response practice
User reports a suspicious email but did not click.
  • Open or create the incident ticket and preserve the original email if available.
  • Check sender, reply-to, return-path, SPF, DKIM, DMARC, subject, links, attachments, and message headers.
  • Check URL/domain reputation in approved tools. Do not browse links directly from your workstation.
  • Search mail gateway for other recipients and quarantine/purge if malicious.
  • Document as attempted phishing, include evidence, scope, user action, and whether containment was needed.
User clicked the link but did not enter credentials.
  • Confirm exact user action and time clicked.
  • Review proxy/DNS/browser logs for the URL and any redirects or file downloads.
  • Check endpoint telemetry for new processes, downloads, scripts, browser extensions, or payload execution.
  • Scope other recipients and clicks across email/security logs.
  • Contain only if there is execution, download, suspicious redirect, or follow-on activity.
User entered credentials on a phishing page.
  • Treat as credential compromise even if no obvious damage is visible yet.
  • Reset password, revoke active sessions/tokens, verify MFA methods, and check for MFA fatigue or device registration changes.
  • Review sign-in logs before and after the click: IP, geo, user agent, impossible travel, risky sign-ins.
  • Check mailbox rules, forwarding, OAuth grants, recent file/cloud access, VPN logons, and privileged activity.
  • Search for other users who received/clicked the same email and document containment actions.
User opened a malicious attachment.
  • Collect filename, hash, sender, recipient, time opened, and attachment type.
  • Check EDR for process tree: Office/PDF/archive spawning PowerShell, cmd, wscript, mshta, rundll32, regsvr32, or downloads.
  • Hash the attachment with SHA256 and check approved reputation/sandbox tools.
  • If payload executed, isolate the host and scope by hash, command line, destination IP/domain, and related email recipients.
  • Remediate persistence and document whether this was blocked, attempted, or successful execution.
Business email compromise / fake invoice request.
  • Preserve the email and verify whether this is spoofing, lookalike domain abuse, or a compromised internal/vendor account.
  • Check financial action taken: payment sent, banking info changed, invoice approved, or only attempted.
  • Review mailbox login activity, forwarding rules, OAuth grants, and vendor communication history.
  • Escalate quickly to finance/legal/management if payment or sensitive business data is involved.
  • Document loss exposure, affected parties, containment, and recommended controls.

Real-World Attacker Scenarios

How to identify and respond
Initial access through VPN account compromise.
  • Check failed/successful logons, source IP, geo, MFA, device, user agent, and normal user pattern.
  • Review what internal systems were accessed after VPN connection.
  • Contain by disabling the account, revoking sessions, forcing password reset, and reviewing MFA methods.
  • Scope for lateral movement, privilege escalation, file access, and additional compromised accounts.
Drive-by download or malicious browser redirect.
  • Start with proxy/DNS/browser history and identify the redirect chain.
  • Check endpoint downloads, process execution, browser extension changes, and EDR detections.
  • Hash downloaded files and search for same hash/path across environment.
  • Block malicious domains/URLs and isolate endpoint if execution occurred.
Living-off-the-land activity using PowerShell or cmd.exe.
  • Do not trust a process just because it is a Windows binary.
  • Inspect parent process, command line, encoded content, child processes, user context, and network connections.
  • Check Event IDs 4103/4104, process creation logs, scheduled tasks, services, and registry run keys.
  • Contain if behavior shows payload download, credential access, persistence, lateral movement, or exfiltration.
Web application attack: SQL injection or XSS.
  • Review WAF, reverse proxy, web server, application, and database logs.
  • Determine whether payloads were blocked, caused errors, or successfully accessed/changed data.
  • Identify vulnerable endpoint, source IPs, user accounts, session IDs, and affected records.
  • Escalate to app owners for fix, add temporary WAF rules if appropriate, and document evidence.
Insider threat or unusual data access.
  • Validate access pattern against job role, manager approval, historical behavior, and business context.
  • Review file access, cloud downloads, USB events, email forwarding, printing, and external sharing.
  • Keep language factual and avoid accusation. Escalate through proper HR/legal/security channels.
  • Document exactly what happened, where data moved, and who authorized next steps.
Exposed vulnerable internet-facing service.
  • Confirm exposure, asset owner, business criticality, vulnerability details, and exploitability.
  • Check logs for exploitation attempts or successful compromise.
  • Coordinate patching, temporary firewall restriction, service removal, or compensating controls.
  • Rescan with Nessus/Tenable and document remediation validation.

What Would You Do?

About a dozen practical CSIRT/SOC interview examples
1. Splunk fires an alert for a suspicious login.

I would start in Splunk because that is where the alert came from. I would confirm the search logic, time range, user, source IP, destination, and whether the login succeeded. Then I would pivot to identity logs, VPN logs, endpoint data, and geo/impossible-travel context. If the account looks compromised, I would escalate to disable/reset the account, revoke sessions, and document the timeline.

2. EDR alerts on encoded PowerShell.

I would start in EDR because process evidence is the center of the alert. I would review parent process, child processes, command line, user context, hash, network connections, and whether the command was blocked or executed. Then I would check PowerShell logs, scheduled tasks, run keys, and SIEM for similar activity. I would contain if there is malicious execution, persistence, credential access, or lateral movement.

3. A user reports clicking a phishing link.

I would start with the user report and email evidence. I would ask what action occurred: opened only, clicked, entered credentials, downloaded a file, or approved MFA. Then I would review email headers, URL reputation, attachment/hash reputation, proxy logs, browser/download evidence, sign-in logs, and mailbox rules. If credentials were entered, I would reset the password, revoke sessions, check MFA, and search for other recipients.

4. Firewall shows connection to a known malicious IP.

I would first determine whether the traffic was allowed or blocked, inbound or outbound, and whether a session completed. Then I would identify the internal host, user, process if available, destination reputation, DNS history, and any related EDR/SIEM alerts. If the connection was allowed and tied to suspicious process behavior, I would isolate the host or block the indicator while scoping for related activity.

5. Repeated login failures followed by a successful login.

I would compare the failed and successful attempts by source IP, user, device, geography, time, MFA status, and normal user behavior. If it is a privileged account, unusual source, impossible travel, or followed by suspicious activity, I would treat it as high severity. Next actions may include disabling the account, password reset, session revocation, and checking what the account accessed after login.

6. Ransomware indicators appear on one endpoint.

I would treat this as critical if I see mass file renames, encryption behavior, ransom note creation, shadow copy deletion, backup tampering, or lateral movement. I would isolate the host immediately, preserve evidence where possible, identify affected shares, check for spread, and escalate to incident response leadership. I would document impact and containment actions quickly because business decisions may be time-sensitive.

7. Malware hash appears in VirusTotal but no EDR alert fired.

I would not assume compromise from reputation alone. I would verify whether the file exists internally, where it is located, whether it executed, who downloaded it, and whether the hash appears on any other systems. I would use EDR, SIEM, file path data, proxy/download logs, and sandbox/reputation context. If the file executed or appears widespread, I would escalate containment and hunting.

8. You find a suspicious scheduled task.

I would inspect the task name, author, command, trigger, run context, creation time, and related parent process. Then I would check whether that timestamp lines up with suspicious logons, PowerShell, file drops, or network activity. If it appears malicious, I would preserve evidence, disable/remove the persistence mechanism through approved response procedures, and hunt for the same task across other endpoints.

9. A ServiceNow ticket says “possible data exfiltration.”

I would clarify the evidence behind the claim first. Then I would identify affected user/host/data, time window, destination, volume, protocol, and whether transfer was allowed or blocked. I would review proxy, firewall, DNS, DLP, cloud storage, VPN, and endpoint evidence. If sensitive data likely left the environment, I would escalate immediately and keep the ticket updated with facts, uncertainty, and next actions.

10. A vulnerability scan shows critical findings on an internet-facing host.

I would validate asset exposure, criticality, exploitability, patch status, and whether there are signs of exploitation. Then I would coordinate remediation priority with the system owner, check compensating controls, and ask whether temporary mitigation is needed. If exploit activity is seen in logs or EDR, it becomes an incident investigation, not just vulnerability management.

11. An executive asks for a non-technical incident update.

I would summarize what happened, what systems/users are affected, known business impact, what has been contained, what is still being investigated, and the next update time. I would avoid unnecessary jargon and clearly separate confirmed facts from assumptions. The goal is to support decision-making without hiding uncertainty.

12. You are not sure whether to contain or keep investigating.

I would base the decision on active risk. If there is active malware, lateral movement, privileged account compromise, exfiltration, ransomware behavior, or business-critical impact, I would contain quickly and preserve evidence as much as possible. If the signal is weak or blocked with no follow-on activity, I would continue validating and scoping before disruptive action.
